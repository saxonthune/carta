# CLI User Flow

Two-phase workflow: hydrate a repo with a `.rhidoc/` workspace, then operate on it.

## Phase 1: Hydrate

A user (or their AI agent) installs the CLI and initializes a workspace in their project.

```
pip install rhidoc
cd my-project
rhidoc init
```

### Portable mode

For collaborators who don't want to install via pip, `rhidoc init --portable` dumps editable Python scripts directly into the `.rhidoc/` directory. These scripts are raw Python (stdlib only, no dependencies) and can be read, modified, and extended:

```bash
# First user (has pip)
rhidoc init --portable

# Collaborator (no pip needed, just python3 >=3.10)
python3 .rhidoc/rhidoc.py regenerate
python3 .rhidoc/rhidoc.py make 00-codex my-doc
```

The portable scripts make `.rhidoc/` a self-contained unit — documentation and tooling travel together. Copy the directory to another repo and it carries its own scripts.

To update an existing workspace's scripts after upgrading via pip:

```bash
rhidoc portable
```

Portable layout:
```
.rhidoc/
  rhidoc.py          <- main entry point (edit freely)
  _scripts/         <- library modules
  MANIFEST.md
  00-codex/
  ...
```

`rhidoc init` creates:
```
my-project/
  .rhidoc/
    workspace.json          <- workspace metadata
    MANIFEST.md             <- auto-generated index
    AGENTS.md               <- generated agent wiring (how to work in the workspace)
    00-codex/
      00-index.md           <- how to read this workspace
  .claude/
    skills/
      rhidoc-cli/
        SKILL.md            <- AI agent CLI reference
      docs-development/
        SKILL.md            <- doc-authoring skill
      rhidoc-setup/
        SKILL.md            <- first-time setup & health diagnostics
```

### Hydrated Files

| File | Purpose | Source template |
|------|---------|----------------|
| `.rhidoc/workspace.json` | Workspace metadata, external ref paths | `templates/workspace.json` |
| `.rhidoc/MANIFEST.md` | Machine-readable doc index (auto-generated by `regenerate`) | Generated |
| `.rhidoc/AGENTS.md` | Standard agent wiring — read-MANIFEST-first, structural-vs-content edits, ref syntax, codex pointers | `templates/AGENTS.md` |
| `.rhidoc/00-codex/00-index.md` | How to read this workspace, CLI quick reference | `templates/00-index.md` |
| `.claude/skills/rhidoc-cli/SKILL.md` | CLI command reference for AI agents (Claude Code) | generated by `ai_skill.generate_skill_content` |
| `.claude/skills/docs-development/SKILL.md` | Doc-authoring skill | `templates/docs-development-skill.md` |
| `.claude/skills/rhidoc-setup/SKILL.md` | First-time setup and workspace health diagnostics (invoke with `/rhidoc-setup`) | `templates/rhidoc-setup-skill.md` |

Templates are bundled in the `rhidoc-cli` Python package at `rhidoc/templates/`. The `init` command reads them, substitutes `{{title}}` / `{{dir_name}}`, and writes to the project directory. `rhidoc init --rehydrate` re-syncs the codex docs, `AGENTS.md`, and skills from the installed version, leaving project-authored docs untouched.

These hydrated files are derived artifacts, not authored content — they must not carry project-specific, load-bearing information (that belongs in the other groups, or in authored skills). `rhidoc init --rehydrate --check` reports drift and exits non-zero if any hydrated copy differs from its packaged source, so a CI step (`make check-hydration`) can block a PR that edits a hydrated copy without updating the template or generator behind it.

The `.rhidoc/` directory is committed to version control alongside the project's source code, so its generated `AGENTS.md` travels with the repo. The `.claude/skills/` files are also committed — they provide workspace-aware knowledge to any AI agent working in the repo. `AGENTS.md` carries the workspace rules so the project's own `CLAUDE.md` only needs a one-line pointer to it (printed by `init`), keeping per-run context small.

## Phase 2: Operate

The CLI is a multiplexed command that performs deterministic structural operations on the workspace. Users and AI agents invoke it the same way.

### Common operations

```bash
# Add a new doc (parent + slug, appends)
rhidoc make 01-product my-feature

# Add a new doc at an exact position
rhidoc make --at doc01.04 my-pinned-feature

# Insert at an occupied position, shifting that sibling and higher ones up by one
rhidoc make --before doc02.02 my-inserted-feature

# Create a new title group (directory + 00-index.md)
rhidoc make -g 01-product new-subgroup

# Expand a leaf file into a directory with children
rhidoc punch 01-product/03-my-feature

# Move/reorder a doc (insert at a specific position, displacing siblings)
rhidoc move 01-product/03-my-feature --before doc02.01

# Promote a group to root slot 00 (root has no 00-index.md, so slot 0 is open)
rhidoc move doc02 --before doc00

# Delete with automatic gap-closing and ref rewriting
rhidoc delete 01-product/02-old-feature

# Dissolve a directory, hoisting children into parent
rhidoc hoist 01-product/03-my-feature

# Rebuild MANIFEST.md from frontmatter
rhidoc regenerate
```

### Workspace discovery

The CLI finds the `.rhidoc/` directory by walking up from the current working directory, similar to how `git` finds `.git/`. An explicit `--workspace` flag overrides this.

```bash
# From anywhere inside the project
rhidoc regenerate

# Explicit path
rhidoc --workspace /path/to/.rhidoc regenerate
```

### AI agent usage

AI agents invoke the same CLI commands. The deterministic nature of structural operations (numbering, gap-closing, ref rewriting) means agents don't need to reason about filesystem bookkeeping — the CLI handles it.

```
Agent reads MANIFEST.md -> understands workspace structure
Agent calls `rhidoc create` -> CLI handles numbering, frontmatter, manifest rebuild
Agent writes doc content -> standard file write
```

## Design Constraints

- **Deterministic**: Same input produces same output. No interactive prompts.
- **Ref-safe**: All structural operations rewrite cross-references in surviving documents.
- **Manifest-synced**: Operations that change structure auto-regenerate MANIFEST.md.
- **Workspace-portable**: The CLI operates on any `.rhidoc/` workspace, not just Rhidoc's own.
